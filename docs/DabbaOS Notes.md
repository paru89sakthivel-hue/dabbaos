## 1. Fixing the IAM permission error (before Task 1)

- **What happened:** EC2 showed a 403 "not authorized" error for my IAM user.
- **Why:** IAM is deny-by-default. A new user can do nothing until a policy is attached.
- **Fix:** signed in once as root (with MFA), attached AdministratorAccess to my IAM user, signed out of root, and went back to the IAM user.
- **Remember:** daily work is as the IAM user, never root. README must say production would use least privilege (only the permissions each job needs).

## 3. Task 2: Security group `dabbaos-sg` (the firewall)

| Rule | Port | Source | Why |
| --- | --- | --- | --- |
| SSH | 22 | My IP only | Only I can log in; bots scan the internet for open SSH |
| HTTP | 80 | Anywhere | Let's Encrypt must reach port 80 to verify my domain; Caddy redirects HTTP to HTTPS |
| HTTPS | 443 | Anywhere | Public access to n8n through Caddy |

- Port 5678 (n8n) stays closed on purpose.
- Exactly 3 inbound rules (success criterion 6).
- **Lesson learned:** My IP is saved as a fixed number. If my network changes (Wi-Fi vs hotspot, VPN), SSH times out. Fix: edit the rule and re-select My IP (or enter it by hand with /32). Never use 0.0.0.0/0 for SSH.

## 5. Task 4: SSH (secure remote login)

```bash
chmod 400 dabbaos-key.pem
ssh -i dabbaos-key.pem ubuntu@PUBLIC-IP
```

- `chmod 400`: SSH refuses keys other users could read.
- User is always `ubuntu` on this image.
- Type the full word `yes` at the first-connection prompt.
- **Lessons learned:**
  - Don't type the `<` `>` brackets from examples. Your Mac treats them as special symbols (that caused the zsh parse error).
  - If SSH just hangs with no output, it is the firewall not matching my IP, not a typing problem.
  - Ctrl+C (control key, not command) stops a hanging command.

## 7. Task 6: The three stack files in `~/dabbaos`

### `.env` (secrets and settings, server only)

- `DOMAIN`: my DuckDNS domain.
- `N8N_ENCRYPTION_KEY`: random 64-character key generated by `openssl rand -hex 32`.
- **Why the key matters:** n8n uses it to encrypt saved credentials (Gemini, Telegram, Sheets). Lose it and they become unreadable. Saved in my password manager.
- Never commit `.env`. The repo gets a `.env.example` with placeholders only.

### `docker-compose.yml` (what to run)

- Defines two containers, n8n and caddy.
- **n8n has no `ports:`**: nothing from the internet can reach it directly. It is only reachable through Caddy (this is success criterion 3).
- **caddy publishes 80 and 443**: it is the one front door. It handles HTTPS, redirects HTTP to HTTPS, and proxies requests to n8n over Docker's private network.
- `restart: unless-stopped`: containers come back after a reboot.
- Volumes `n8n_data`, `caddy_data`, `caddy_config`: storage that survives container re-creation. Workflows live in `n8n_data`.
- `GENERIC_TIMEZONE` / `TZ` = Asia/Kolkata: makes n8n use IST (success criterion 8).
- `N8N_PROXY_HOPS=1` and `WEBHOOK_URL`: tell n8n it sits behind one proxy and what its public address is.
- The `'EOF'` quotes when creating the file stop the shell from filling in `${DOMAIN}`; Docker does that later from `.env`.

### `Caddyfile` (how to route)

```
{$DOMAIN} {
    reverse_proxy n8n:5678
}
```

- A **reverse proxy** takes public traffic and passes it to a private service.
- Caddy also gets and renews the free Let's Encrypt certificate automatically.
- `n8n:5678` works because containers find each other by service name.
- **Lesson learned:** my first `ls -la` showed the Caddyfile was missing. Always verify a file exists (and starts with `-rw`, not `d`) before starting the stack.

- `crontab -l` shows the @reboot line. Note: `-l` is the letter L, not the number 1. Escape nano with Ctrl+X, then Y, then Enter.

### Timezone lesson (candidate for my "bug I found" story)

- The container had `TZ` and `GENERIC_TIMEZONE` set to Asia/Kolkata (checked with `docker exec dabbaos-n8n-1 env`).
- But in the Code node, plain `new Date().toString()` printed UTC, while n8n's own `$now.toString()` printed +05:30.
- **Use `$now` in Chapter 3** when filtering today's orders in IST.
- I did not verify why plain `new Date()` stays on UTC in my n8n version, so I will not claim a reason.
- India is 1 hour 30 minutes ahead of Dubai. Seeing 20:31 in n8n when it is 19:01 in Dubai is correct, not a bug.
